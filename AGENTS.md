# Wolvic agent notes

Wolvic is an Android XR browser (Java/Kotlin + C++/CMake) with multiple backends and device platforms. Trust Gradle/config/scripts over README prose when they disagree.

## Key commands (Windows: `gradlew.bat`; CI uses `./gradlew`)

- Build (examples from CI): `./gradlew assembleNoapiArm64GeckoGeneric`, `./gradlew assembleNoapiX64GeckoGeneric` (external/no-device SDK path).
- Unit tests (CI): `./gradlew testNoapiArm64GeckoGenericDebugUnitTest` and `./gradlew testNoapiX64GeckoGenericReleaseUnitTest`.
- Internal/device flavors follow the same task shape: `assemble<Platform><Abi><Backend><Store>` (see `.github/workflows/ci-internal.yaml` matrix).
- CI environment: JDK 21, Gradle 8.13 (`.github/workflows/build.yml`). Android toolchain in `app/build.gradle` uses Java 21 toolchain / Java 11 source+target; `compileSdk 36`, `minSdk 26` (flavor-dependent), AGP from `gradle/libs.versions.toml`.

## Build matrix (high signal)

Defined in `app/build.gradle` with `flavorDimensions = [platform, abi, backend, store]`:
- Platforms: `oculusvr`, `picoxr`, `pfdmxr`, `qiyu`, `lynx`, `spaces`, `aosp`, `hvr`, `noapi`, `visionglass`.
- ABIs: `arm64` (`arm64-v8a`), `x64` (`x86_64`). `x64` variants are only built for `noapi` and `aosp`.
- Backends: `gecko` (default), `chromium`, `webkit`. `chromium`/`webkit` variants exist only when local AAR paths are set in `local.properties` (`chromium_aar` / `webkit_aar`; see `isChromiumAvailable`/`isWebKitAvailable`).
- Stores: `generic`, `metaStore` (Oculus only), `mainlandChina` (HVR/VisionGlass/PicoXR/Qiyu only), `magicleap` (AOSP x64 only).
- Some flavors override `applicationId`/suffix, manifests, resources, and `BuildConfig` (notably China/homepage/speech services in the variant loop at end of `app/build.gradle`).

## Local config (gitignored; do not commit)

- `local.properties`: SDK paths plus Wolvic-specific keys read by `settings.gradle` into `gradle.ext` as `localProperties.*`. Used for backend AARs and GeckoView dependency substitution (`dependencySubstitutions.geckoviewTopsrcdir`, `geckoviewTopobjdir`, `geckoviewTopobjdirX64`). Deprecated `geckoViewLocalArm`/`geckoViewLocalX86` properties throw.
- `user.properties`: loaded by `settings.gradle` as `userProperties.*` (values are logged). Known flags in build logic include `simultaneousDevProduction`, `useDebugSigningOnRelease`, `useStaticVersionCode`, `disableCrashRestart`, `HVR_APP_ID`, `otelEndpoint`, `enableServo` (`:servo` module included only when enabled). Treat as local/dev-only.
- Secrets/tokens/artifacts to keep out of commits: `.mls_token` (read into `BuildConfig.MLS_TOKEN`), `app/agconnect-services.json`, `*.jks`, `oculussig_*`, `third_party/` contents as applicable.

## Repo structure / non-obvious layout

- `app/` is the main Android module. `settings.gradle` includes only `:app` (+ optional `:servo`).
- Main Java/Kotlin source dirs are unconventional (`app/build.gradle`): `app`, `src/common/shared`, `src/main/cpp/vrb/android/java`; plus flavor/variant dirs such as `src/common/gecko|chromium|webkit`, `src/openxr/...`, platform dirs (`src/oculusvr`, `src/hvr`, `src/picoxr`, `src/qiyu`, `src/aosp`, `src/noapi`, `src/visionglass`, etc.), store/China dirs, and debug/release manifest overlays.
- Native code: `app/CMakeLists.txt` builds shared library `native-lib` and links `vrb`. Platform/feature flags (`NOAPI`, `VISIONGLASS`, `HVR`, `AOSP`, `OPENXR`, `OCULUSVR`, `SPACES`, `QIYU`, `LYNX`, `PICOXR`, etc.) select C++ sources and loaders. OpenXR headers come from Gradle `OpenXR::headers`; loader strategy differs by platform (some copy loaders from `third_party/`).
- C++ submodules are declared in `.gitmodules` under `app/src/main/cpp/`: `vrb`, `tinygltf` (`igalia.com/wolvic` branch), `KTX-Software` (`4.2`). `third_party/` is a separate gitignored checkout for proprietary/device SDKs; CI pins it via `third_party_hash` (`.github/workflows/build.yml`).

## Backend/runtime gotchas

- Gecko/WebXR on the prebuilt Maven GeckoView: Qiyu builds define `WOLVIC_GECKOVIEW_EXTERNAL_VR_19`, so `app/src/main/cpp/moz_external_vr.h` selects `moz_external_vr_v19.h` (stock `FIREFOX_153_0_RELEASE`: `kVRExternalVersion = 19` / `SHMEM_VERSION "0.0.12"`); all other flavors keep `moz_external_vr_v21.h`. `ExternalVR.cpp` maps Wolvic's richer API onto v19 under that macro (translation-only `eyeTranslation`, single `displayState.blendMode`, no `ImmersiveXRSessionType`, no v21 controller enums). Keep `moz_external_vr_v19.h` byte-identical to the matching Gecko release header. Gecko's `VRShMem::CreateShMemForAndroid()` silently drops the shmem when `version`/`sizeof(VRExternalShmem)` differ: no log line, inline WebXR and `navigator.xr` still work, but `isSessionSupported('immersive-vr')` is false (immersiveweb.dev then shows only "WebXR Device API / Gamepads / Inline"). The v21 path still requires a GeckoView built from `Igalia/wolvic-gecko-patches` (`gecko-153esr`) plus `dependencySubstitutions.geckoviewTopsrcdir` in `local.properties`.
- Chromium backend is not a normal local Gradle-only build: it requires building/fixing AARs and copying assets from an external Chromium checkout (`CHROMIUM.md`). Only then do Chromium variants appear.
- Gecko config check: `app/src/main/res/raw/fxr_config.yaml` must end with a newline because runtime code appends prefs; `tools/gradle/checkGeckoConfigFile.gradle` enforces this for Gecko variants on preBuild. If you edit that file, preserve the trailing newline.
- Versioning: `tools/gradle/versionCode.gradle` generates a time-based `versionCode` by default (prints it during config). `userProperties.useStaticVersionCode=true` overrides; PicoXR store builds apply a store-specific offset.

## Qiyu platform (QIYU 3 / Dream / Dream Pro / Lenovo Legion VR700 / MIX / Qiyu X)

- Variant shape: `assembleQiyuArm64GeckoGeneric[Debug|Release]` (and `MainlandChina` store). Platform is OpenXR (`-DQIYU -DOPENXR`), arm64-only by current filters.
- Qiyu Native SDK (ALVR-compatible family; Qiyu_Native_SDK_v1.0.0, `libqiyuapi.so` / `qiyu_GetControllerData(left,right)`) is loaded from `localProperties.qiyuSdkDir`/`qiyu_sdk_dir` or `third_party/qiyu` (`Include/` + `Lib/*release*.aar`: `qiyuapi`, `qiyivrsdkcore`, `sxrApi`). `third_party/` is gitignored; do not commit SDK binaries.
- Controller bridge (ALVR/alvr-openxr-v20 patterns): Qiyu `PlatformActivity` loads `qiyivrsdkcore/sxrapi/ashreader/qiyuapi` via `System.loadLibrary` **before** `NativeActivity` starts OpenXR, so the app classloader owns `libsxrapi.so` first (important on the Monado/VR700 runtime). It then stores the Activity and enables the bridge only on Qiyu X. `app/src/qiyu/cpp/QiyuControllerBridge.*` (hooked in `OpenXRInputSource.cpp` under `QIYU`) calls `qiyu_Init` lazily on the first controller/haptic update after the OpenXR session is up (no `qiyu_StartVR`, to avoid OpenXR session conflict) and polls `qiyu_GetControllerData` as fallback for incomplete OpenXR controller input. It can also apply qiyuapi pose/haptics when available.
- Single-APK build (important): the default Qiyu build packages the Qiyu SDK AARs/classes/native libs and sets `BuildConfig.QIYU_CONTROLLER_BRIDGE=true`, so one APK covers QIYU 3/Dream/Dream Pro/MIX/VR700/Qiyu X (ALVR-style). On Dream/VR700 the runtime's SXR stack provides display/controllers; the app's `SxrApi` is present but is initialized only after the app libs are already loaded, so it no longer shadows the runtime's `sxrInitialize`. `-PqiyuControllerBridge=false` builds the old pure-OpenXR APK (no SDK classes/libs) as a fallback.
- `app/src/qiyu/AndroidManifest.xml` must keep `WAKE_LOCK` (with `tools:node="replace"`) or `OffscreenDisplay`/`Presentation` crashes on launch. Qiyu Dream firmware `A091` (and `iQIYI-A6*`, `Lenovo Legion VR700`) maps to `device::QiyuDream` in `DeviceUtils.cpp`.
- Device detection includes Qiyu/IQIYI model heuristics and Lenovo Legion VR700/Dream-series mapping. Real-device validation is required (hallychou/ALVR-QIYU used full SXR rendering for Dream/VR700/QIYU 3; Wolvic uses OpenXR and depends on the device/runtime OpenXR path plus the controller bridge).
- Native builds require initialized submodules (`git submodule update --init --recursive` for `app/src/main/cpp/{vrb,tinygltf,KTX-Software}` and vrb deps).

## Lessons learned on device (Qiyu X / MIX / Dream) — do not repeat these

- **Never strip `com.qualcomm.**` / `com.qiyi.**` from ProGuard/R8 on Qiyu.** SXR's native `sxrInitialize()` resolves `com/qualcomm/sxrapi/SxrApi` with JNI `FindClass`. If R8 removes it you get `Failed to initialzie SxrApi Java class` -> `@qiyu_Init, fail to param init` -> `qiyu_Init=0`, and the pending `ClassNotFoundException` later aborts the process (`thread.cc: No pending exception expected`). That exact combination was a shipped regression once.
- **`qiyu_Init` returning false is not fatal on Qiyu X.** `PlatformActivity` loads `qiyivrsdkcore/sxrapi` first (`VRSDKCore: JNI_OnLoad`), so the SXR stack is already up and `qiyu_IsControllerInit()` is true. Treat `init==0 && controller_init==1` as usable; only bail when both are false. Bailing gave the classic "black screen then exit".
- **Call ordering matters (`third_party/qiyu/Include/QiyuApi.h`).** `qiyu_StartEye` must run *after* the eye FBO is bound and *before* that eye is rendered; `qiyu_EndEye` after the eye. `qiyu_StartVR(window)` on `APP_CMD_START/RESUME/INIT_WINDOW`; `qiyu_EndVR` on `APP_CMD_PAUSE/TERM_WINDOW`. `qiyu_Update(dt)` before rendering. A stale SXR session (no `EndVR`) also presents as a black screen on the next launch.
- **Native SXR delegate beats OpenXR on Qiyu.** `DeviceDelegateQiyu` (`app/src/qiyu/cpp/`) submits straight to the SXR compositor and holds 71.8 fps at 1920x1920; WebXR still works because Gecko drives it through `ExternalVR`, not OpenXR. The OpenXR path on the same hardware goes through Monado's VR700 SXR backend, where the app FOV (60x63 deg) is narrower than the panel (82x92 deg): SXR warp expands the image (logged `Frustum Display Width/Height Scale 1.369/1.452`) and starves on frame pacing (`No valid frame to warp`) producing moving vertical/snowflake artifacts. That is a runtime-side double-warp, not a Wolvic shader bug.
- **`ANativeWindow_setFrameRate not found`** on VR700 firmware means our refresh-rate request is only honoured compositor-side; the panel keeps 90 Hz while the app may sit at ~61-80 Hz. Do not "fix" missing frames by only lowering resolution; check the compositor interval in logcat (`compositor_request_display_refresh_rate`).
- **MIX (A081) has no `org.khronos.openxr.runtime_broker`** on the firmware seen here; OpenXR returns `XR_ERROR_RUNTIME_UNAVAILABLE`. The build must degrade instead of throwing. MIX also lacks `libStereoRectifyWrapper.so`, so `SxrApi.<clinit>` (which `System.loadLibrary("sxrapi")` -> dependency chain) fails there; keep the class (R8) but expect SXR to be unusable on that firmware unless the vendor lib is present.
- **A device delegate must call `ControllerDelegate::CreateController`.** `ControllerContainer` only acts on controllers that exist in its list; without the call every `SetEnabled`/`SetTransform`/`SetButtonState`/`SetMode`/`SetBeamTransform` is a silent no-op, so the controller has no model, no laser beam and cannot interact. `DeviceDelegateQiyu::SetControllerDelegate` creates both entries (model index `i`, generic trigger model) and leaves them disabled until SXR reports a connection. Also feed the beam: qiyuapi has no aim pose, so use the grip pose as the aim (`SetBeamTransform(aimOffset)` standalone, `SetTransform(grip*aimOffset)` + `SetImmersiveBeamTransform(grip)` immersive). A grip-to-aim tilt can be dialled in live with `adb shell setprop debug.wolvic.qiyu.aim "pitch,yaw,roll"` (degrees, identity when unset; re-read once a second).
- **Use the Qiyu SDK poses exactly as the official native sample does.** `Qiyu_Native_SDK_v1.0.0/Samples/QiyuVR_NativeActivity/app/jni/QYModel.cpp` builds the controller model as `translate(pos.x, pos.y [- trackingOffset in ground mode], pos.z) * quat(w,x,y,z)` and renders it with the view matrix from `qiyu_GetViewMatrix`. The SDK space is right-handed Y-up / -Z-forward, the same as Wolvic. Do **not** invent axis flips: `(x,-y,-z)` mirrors yaw/pitch (point left, beam goes right) and puts controllers above/behind the head. Ground vs device mode matters: `qiyu_GetTrackingOriginMode()`; in `TM_Ground` subtract `trackingOffset` from the Y of the head and controllers, in `TM_Device` use the pose unchanged.
- **Follow the official Qiyu input mapping.** `Qiyu_Native_SDK_v1.0.0/Samples/QiyuVR_NativeActivity/app/jni/QiyuVR_NativeActivity.cpp::UpdateButtonState` uses `triggerForce > 0.5f`, `gripForce > 0.5f`, and the `button` press bits for A/X/B/Y/menu. A `0.2f` threshold (used earlier here) makes the trigger fire on mere touch. Some Qiyu X firmware reports only `buttonTouch` (`0x1` while `button=0x0`, `triggerForce=0.00`); `DeviceDelegateQiyu::UpdateController` then requires a deliberate 250 ms touch hold (never a first-frame latch) and disables the fallback entirely once any analog or press value arrives.
- **Passthrough on Qiyu is a system service, not a renderer feature.** The rendering app cannot start the cameras from its own compositor; the Qiyu system owns VST. Verified on a Qiyu X device log:
  - `com.qiyi.seethroughservice/.SeethroughService` is commanded with an explicit start whose `mode` extra selects the operation: `3` = (re)apply the passthrough layer model, `1` = start the RGB cameras, `2` = stop. Device log: `SeethroughService: onStartCommand mode = 1` → `VstManager: startSeethrough: started ref count = 1` → `VstManager: startCamera: started` → `seethrough_xr: startSeeThrough wait_for:0` → `NotifyVstStarted`.
  - Who drives it: the Qiyu OpenXR host (`QiyuOXRCore`, which embeds Monado as `monado-ipc-client`) logs `yyj PassthroughStart` / `yyj PassthroughStop` immediately before the service start command. So an OpenXR app enables passthrough through the runtime, and the runtime starts the service.
  - `content://com.iqiyi.vr.provider/vst/1` is `RgbCameraStatus` and `.../vst/2` is `AppVstStatus`. **Both are status reports, not commands.** Writing `AppVstStatus=1` does not start anything — this is why the earlier "provider passthrough" attempt set `AppVstStatus` but left `RgbCameraStatus=0`.
  - App side: when VST is running the compositor blends the cameras behind the eye buffer, so the app must clear with **alpha 0** and stop drawing the opaque root/skybox. Wolvic already does both: `BrowserWorld::UpdateEnvironment()` returns early when `DeviceDelegate::IsPassthroughEnabled()`, and the opaque root is skipped in `BrowserWorld::DrawEye`. The official Unity sample proves the contract: `QiyuSeeThrough` sets `clearFlags = SolidColor` and `backgroundColor = (0,0,0,0)` on `AppOpen`.
  - Official API surface: `Runtime/Scripts/QiyuSeeThrough.cs` in `Qiyu_UnityXR_SDK_v1.6.1.zip` — `QiyuXRCore.EnableSeeThrough(bool)` → `QVR_EnableSeeThrough` in `libQiyuXRCore.so`, plus `QVR_SetSeeThroughCallback`, `QVR_GetPassthroughCapabilities`, `NativeMethods.UseVstNeckMode`. `QiyuXRCore.aar`'s `libQiyuXRCore.so` links against `libsxrapi.so` **and** `libsxrapi.qti.so`, so it needs the newer 5 MB `libsxrapi.so` and cannot be loaded next to the old 2.2 MB one.
  - So the only documented third-party route that works with the old `qiyuapi` renderer is starting `com.qiyi.seethroughservice` directly (`QiyuSeeThrough.java`). If the service refuses a third-party caller, the remaining option is porting frame submission to the new `SxrApi`/`SvrView` (FxR) or Unity `QVR_*` (Moon VR) path.
  - **Current status (1.11.13):** the in-app vendor VST bridge (`app/src/qiyu/cpp/QiyuVst.{h,cpp}`) is **inert** and stays out of the APK. 1.11.12 called `startSeeThrough(1, 0, &cb, 0)` and crashed every time with `SIGSEGV` in `CameraClientImpl::startCameraRGB(void*)+288` on the detached camera thread spawned by `startSeethroughCamera`: the object returned by `getQvrCameraClientInstance()` has an ABI-incompatible vtable, because the camera client is supposed to come from `libsxrapi.so`'s `SvrCameraManager` and our renderer must ship the 2.2 MB 2022 `libsxrapi.so`. The 5 MB 2023 `libsxrapi.so` (which Firefox Reality 12.3 ships, together with `libqiyuinterface`/`libseethrough-core`/`librelocationsdk`/`libQiyuXRCore`) is the matching build and drives VST from its own loop via `sxrEnableSeeThrough` -> `SvrStartSeeThrough` -> `startSeeThrough`, but swapping it black-screens the `qiyuapi` renderer at 71.8 fps and only one `libsxrapi.so` can exist per process. Do **not** call `startSeeThrough`/`startSeethroughCamera` from the app: the third argument is not a callback (the real signature is `startSeeThrough(int flags, int a1, void* a2, int waitForFrame)`, and `a2` becomes `startCameraRGB`'s `void*` argument), and no argument value avoids the fault. `QiyuVst` only loads with `debug.wolvic.qiyu.vst=1`, and `libcameralibrary2.so`/`libseethroughsdk.so` are no longer packaged. `VRBrowserActivity.togglePassthrough` now keeps the opaque scene when no pipeline started instead of clearing to alpha 0 over black, and the ladder logs under the low-volume `QIYUVST` tag with `rgb`/`app`/`sys` provider statuses. `docs/qiyu-passthrough-handoff.md` sections 11-13 have the full evidence.
  - **The service is addressed by ACTION (1.11.15).** `dumpsys package com.qiyi.seethroughservice` declares `Service Resolver Table / Non-Data Actions: org.freedesktop.monado.vst -> com.qiyi.seethroughservice/.SeethroughService`. An intent that sets the component directly has `action = null` and the service logs `onStartCommand mode = 0` no matter which extras it carries - that is why 1.11.11-1.11.14 were ignored, and why `am startservice -n <pkg>/<cls> --ei mode 1` from shell also left `RgbCameraStatus` at 0. It was never a caller-permission problem. 1.11.15 sends `Intent("org.freedesktop.monado.vst").setPackage(...)` with the `mode` int (3 = apply `Passthroughlayermodel`, 1 = start cameras, 2 = stop), then falls back to a String `mode`, then to the component form. Verify from a shell with `adb shell am startservice -a org.freedesktop.monado.vst --ei mode 1` and `content query --uri content://com.iqiyi.vr.provider/vst/1` (`status_value=1`). `QIYUVST` lines are logged at warning level because chatty's per-uid quota drops this app's info lines.
  - Thru3D Media Player does **not** use the service: it is an OpenXR client using `XR_QIYU_passthrough` (`{"enabled":true,"layer":true}`, `actual_blend_mode:2`, `viewport_transparent_bg:true`, 1800x1800, 48-53 fps at 72 Hz). That route needs an OpenXR session and is not available to the native SXR delegate.
  - **Two working routes, confirmed against shipped apps (`docs/qiyu-thru3d-passthrough-rea.md`).** (A) Thru3D Media Player uses the runtime's undocumented OpenXR extension **`XR_QIYU_passthrough`** (`XR_FB_passthrough` with every structure type +200000 and entry points renamed `...QIYU`), submits a `XrCompositionLayerPassthroughFB` (`type 1000318003`, `flags = BLEND_TEXTURE_SOURCE_ALPHA`) beneath all layers, and must call `xrPassthroughLayerSetStyleQIYU` with `textureOpacityFactor = 1.0` or the layer renders at opacity 0 (black). The runtime opens the camera **at `xrEndFrame`** and only while a started passthrough layer is in the frame, which is why alpha-0 alone never worked. This needs the OpenXR delegate; Wolvic already has `OpenXRPassthroughStrategy` + `OpenXRExtensions` plumbing for the FB variant. (B) A real bridge for the `qiyuapi` renderer: **`libseethroughsdk.so`** (+ `libcameralibrary2.so`, 975 KB total, both in the official `svrApi-release.aar`) has **no `libsxrapi.so` in its DT_NEEDED**, exports `startSeeThrough`/`initSeeThrough`/`setParamsSeeThrough`/`drawSeethrough`, and hands camera frames to the app as GL textures - app-rendered VST with the renderer, controllers and 6DoF untouched. Only `android.permission.CAMERA` is required. `com.qiyi.seethroughservice` is a thin wrapper over that library, so calling it directly bypasses the service entirely. `initSeeThrough` needs the EGL context current (call it on the GL thread).
  - **The service ladder is the primary plan.** The earlier "the system only starts it for an OpenXR client" conclusion was wrong: the service is a plain exported `startService` target. The wall was the intent shape (it must carry the `org.freedesktop.monado.vst` action), not the caller.
- **6DoF comes from SXR, not from `qiyu_SetTrackingOriginMode`.** `qiyu_SetTrackingOriginMode` only stores an SDK-side enum (it decides whether `GetViewMatrix` subtracts the ground offset); it does not enable positional tracking. Positional tracking is `sxrSetTrackingMode()` from `libsxrapi.so` (`kTrackingRotation=1`, `kTrackingPosition=2`; mode 3 = positional with rotational fallback). `qiyu_StartVR` already calls `sxrSetTrackingMode(3)` — device log: `sxr: sxrSetTrackingMode : Using application defined tracking mode (3). / Setting tracking mode to positional` and `ControllerHandManager Init isGlobal3Dof:0`. `DeviceDelegateQiyu::EnterVR` re-asserts it and logs `sxr tracking supported/current/set/now` via the `libsxrapi.so` symbols so a genuine 3DoF session is visible in logcat. If the head still feels 3DoF, first check the 1 Hz `QIYU: head raw pos=...` line for changing position.
- **Camera from `qiyu_GetViewMatrix`, controllers from raw `qiyu_GetControllerData`.** That is what the official native sample renders (`matView * matWorld`): invert both eye view matrices for the head/eye transforms, keep controllers raw with the ground-mode offset. Never mix a view-derived head position with the `qiyu_PredictHeadPose` rotation, and never use the predicted pose as the camera with raw controllers — those mixed frames produced the "world follows the head / 0DoF" and misplaced-controller symptoms. `qiyu_PredictHeadPose` and the view matrix disagree on Qiyu X (view head is a point reflection of the raw pose, `raw (-0.05,0.31,0.64)` vs `view (0.05,1.28,-0.64)`); keep the 1 Hz `head raw pos`/`view pos` trace when debugging.
- Useful logcat filters while debugging Qiyu: `QIYU:|native QIYU|sxr |VRSDKCore|ash_reader|QvrSDK:ConCoreS|No valid frame to warp|Fatal signal|Abort message`.
- Reference artifacts used for reverse engineering live outside the repo: `F:\vr-sdks\qiyu\ref\Firefox Reality 12.3.apk.1`, `F:\vr-sdks\qiyu\ref\Wolvic-qiyu-arm64-gecko-generic-debug-itk2026 9 29.apk.1`, and the working comparison client at `F:\alvr-openxr-v20`. Official SDK examples: `F:\vr-sdks\qiyu\Qiyu_Unreal_SDK_v1.5.0.zip`, `Qiyu_UnityXR_SDK_v1.5.0.zip`, headers in `third_party/qiyu/Include/`.

## Practical guidance

- Pick the narrowest variant that matches the change (often `noapi*Gecko*` for logic/unit-testable work; platform/OpenXR/native changes usually need the target platform flavor).
- Read `app/build.gradle`, `settings.gradle`, `gradle/libs.versions.toml`, and the relevant `app/src/<flavor>/` tree before changing build logic or platform behavior.
- Check `.github/workflows/*.yaml` when inferring supported build/test entrypoints; CI is the most reliable executable reference in this environment.
